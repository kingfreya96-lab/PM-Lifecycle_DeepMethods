# 决策权与门控例外 — 让门控真的会拦住错误决策

**问题**：现有契约规定了"什么证据才能通过门控"，但没规定三件事：
**① 这个决策能不能反悔；② 谁有权推翻它；③ 门控被绕过时怎么留痕。**

结果是一个现实里必然发生的情况：**老板说"先做起来再说"**，
执行者绕过门控，流程看起来还在运转——记录卡缺失，但没有任何机制发现它。
等到三个月后产品做砸了，没人知道当初跳过了什么。

本文件补这三个洞。**不是加审批层，是加"绕过也要付代价"的通道。**

---

## 1. 决策可逆性分级

**同一个证据门槛，用在所有阶段上是错的。** 阶段 5 选方向错了可以改（可逆），
阶段 16 发布出去收不回来（不可逆）。用同一套门槛，可逆决策被拖成过度论证，
不可逆决策被"差不多就行"放行。

记录卡必须标出**本次门控裁决的可逆性**：

| 级别 | 含义 | 判断标准 | 证据要求 |
|---|---|---|---|
| **R1 易逆** | 错了随时能改回来，成本接近零 | 改主意不需通知用户、不产生对外影响 | E1/E2 即可（基线要求） |
| **R2 可逆** | 错了能改，但有成本 | 需要回滚 / 通知用户 / 补数据 | 基线 + 至少一条 E1 |
| **R3 难逆** | 很难改回 | 迁移成本高、对外承诺已做出、用户已依赖 | 基线 + E1 + **具名复核人** + 回滚方案已演练 |
| **R4 不可逆** | 基本回不来 | 数据删除、对外发布、不可退的合同/资质 | 基线 + E1 + **具名复核人** + **二次独立复核** + 回滚/退出方案 |

**规则**：
- R3/R4 的门控裁决**不能只有一个人**。校验脚本会检查复核人字段。
- R4 的"二次独立复核"指**第二个人独立重做一次 L1 判断**，
  而不是"负责人自己再看一遍"。同一个人看两遍不算复核。
- 阶段默认级别（写死，避免每次重新判断）：
  阶段 1–6 → R1/R2；阶段 7–9 → R1/R2；阶段 10–13 → R2/R3；
  阶段 14–16 → **R3**；阶段 17–18 → R2（发布后仍可回滚）；阶段 19 → R3/R4。
- 阶段默认级别**只代表"典型情况"**。记录卡可以标更低的级别，
  **但不能标更高**（把可逆决策说成不可逆来拖延，或把不可逆说成可逆来放行，
  都要被质疑）。标更低时要写理由。

**记录卡落点**：「门控裁决」段的「可逆性」字段。

## 2. 门控例外（绕过通道）

**不提供绕过通道 = 逼人造假。** 现实中如果只有"必须走完流程"和"违规"两个选项，
理性执行者会选择**不记录**——因为记录了要挨批，不记录没人知道。

所以：**允许有条件地绕过，但必须显式登记，并且付出可见代价。**

一份记录卡要绕过门控，必须填「门控例外」段：

```
例外类型：紧急上线 / 高管指令 / 时间窗 / 其他
授权人：<具体的人，必须具名>
原裁决若为 STOP/REVISE：为什么仍然推进
被跳过的证据要求：<具体到"缺 E1"或"缺回滚演练">
风险接受人：<谁接受了这个风险，与授权人不是同一人时写清>
补救期限：<何时补齐被跳过的部分>
补救责任人：
```

**校验规则**：

| 情况 | 处理 |
|---|---|
| 门控裁决是 GO/CONDITIONAL，但**没有**例外段 | 正常，不检查例外段 |
| 有例外段，但授权人只写得出"老板"/"上面"/"产品团队" | **报错**——没有具名授权人 = 没有授权 |
| 有例外段，但**没写被跳过的证据要求** | **报错**——不知道跳过了什么，就无法补 |
| 有例外段但**没有补救期限或补救责任人** | **报错**——绕过是延后，不是取消 |
| 例外段存在且五项齐全 | **通过**，并在记录卡头部打「⚠ 含门控例外」标记 |
| 例外被使用，但**下一阶段门控前**没补齐 | **报错**——补救期限到了就得闭合 |

**"被跳过的证据要求"要具体到能被验证。** 写"缺证据"不行，
要写"缺 E1 行为数据（试点组留存）"、"缺回滚演练"。

**代价必须可见**：例外段的存在会在 `workspace.py status` 里显示，
并计入阶段 19 的"流程健康度"统计。反复用例外 = 流程失效的信号，
这时候该修流程，而不是继续用例外。

## 3. 门控的成本上限

**一个门控开三天会，三天后没人想改了。** 流程会退化成服从的仪式——
人在场是为了结束它，不是为了做出判断。

记录卡的「门控裁决」段加一行：

```
门控成本：<门控从发起到裁决实际花了多久 / 花了多少人的时>
```

**规则**：
- 门控成本**超过该阶段时间盒的一倍** → **警告**（不是错误）。
  超时本身不是错，但如果同时裁决 GO 且证据等级不高，要警惕"用时间换信心"。
- **连续两个阶段门控成本超时间盒** → 阶段 19 的流程健康度里记一笔，
  因为这通常说明**时间盒定得不现实**，该调的是时间盒。
- 门控成本**远低于时间盒**（如 1 小时走完阶段 11 PRD 门控）→ **警告**：
  这不是高效，是没做判断。

> 时间盒默认值见 `decision-contract.md` §7。

## 4. 谁能推翻裁决

阶段 12（开发执行）发现新证据推翻原判断时，流程已经要求回到阶段 5/6 重评。
但**没有规定谁能推翻、多久内必须重评、推翻要不要留痕**。

| 情形 | 规则 |
|---|---|
| 阶段 12 发现新证据 | **必须**回阶段 5/6 重评，不允许"已经投入开发"为由自动继续 |
| 谁有权推翻 | **决策责任人本人**（阶段 5/6 的负责人），或其**上一级授权人**。其他人只能**提出重评请求** |
| 推翻必须留痕 | 在原门控裁决旁记一条「被推翻」记录：谁推的、基于什么证据（E 编号）、什么时间 |
| 多久内必须重评 | 收到重评请求后 **5 个工作日**内必须给出裁决（重评 / 维持 / 改判） |
| R3/R4 决策的推翻 | 必须有**新的 E1/E2 证据**，不能仅凭"感觉不对" |

**记录卡落点**：「未决假设」表 + 决策日志。
`workspace.py` 的决策日志（`decisions/gates.jsonl`）是 append-only 的，
推翻记录也写进去，所以**推翻历史本身可追溯**。

## 5. 流程健康度（阶段 19 汇总）

这套流程的失败不是某一次判断错，而是**逐渐退化成填表**。
阶段 19 归档时必须统计这几项：

| 指标 | 健康 | 病态信号 |
|---|---|---|
| 门控裁决分布 | 各类裁决都有分布 | 连续全是 GO（门控变成橡皮章）或连续全是 REVISE（门控全在卡流程） |
| 例外使用次数 | 0–1 次 | 每阶段都用（流程已被绕过，规则成了摆设） |
| 门控成本 vs 时间盒 | 大致吻合 | 系统性超时（时间盒不现实）或系统性秒过（没做判断） |
| 校准命中率 | 逐季上升 | 长期不涨（判断能力没提升，流程只是在记录） |
| 假设推翻率 | 有一定比例 | 长期 0（假设从不回头检验，链条是假的） |

**连续两次全 GO + 零推翻 + 命中率不涨** → 这套流程在该项目上已经失效。
阶段 19 的门控不能是 GO，应当是 REVISE，并写明"要改什么"。
