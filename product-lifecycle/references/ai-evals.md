# AI 评估集（Evals）规范 — AI 产品的质量门控

**这份文件补的是本 skill 最大的结构缺口。** 在它之前，AI 产品阶段只能证明"没崩"，
不能证明"变好了"。有了它，AI 功能的质量才能像代码测试一样被回归、被阻断、被追责。

> 适用范围：任何含模型推理、Agent、RAG、生成、分类、推荐、Copilot 形态的功能。
> 纯规则引擎、纯查询的产品写「不适用及理由」。

---

## 0. 核心立场

**评估集不是"出几道题"，是从真实生产数据里切出来的一块。**

自己编题测出来的分数，只能证明"我写的题我会做"。顶尖团队的做法是：
拿真实的用户输入（带 trace_id、时间、分群、最终有没有被采纳），按真实分布分层抽样，
人工标注期望结果，冻结成黄金集，然后**任何一次改动都要重跑它**。

三条不可让渡的原则：

| 原则 | 含义 | 违反的后果 |
|---|---|---|
| **代表性优先于数量** | 1000 条自己编的简单题 < 80 条分层抽样的真实题 | 测出来的高通过率是假的 |
| **失败模式优先于平均分** | 平均 92% 可以掩盖"合规切片 0%" | 灾难性切片被平均掉 |
| **判分可信度优先于判分速度** | judge 没校准过 = 没判分 | 用 LLM 给 LLM 打分验收自己 |

## 1. 四层评估集

每一层的**来源、用途、隔离规则**都不同。混在一起是最常见的错误。

| 层 | 来源 | 用途 | 规则 |
|---|---|---|---|
| **黄金集 (gold)** | 生产 trace 分层抽样 + 人工标注期望 | 判分基准 | 冻结，只增版本不原地改；改期望值 = 新版本 |
| **留出集 (holdout)** | 同源抽样，**从不给开发/调参的人看** | 防过拟合 | 每次评测只跑一次；看过就作废重建 |
| **对抗集 (adversarial)** | 红队构造：注入、越权、恶意输入、边界长尾 | 安全与滥用 | **容忍度 0**，单独报，不进平均 |
| **回归集 (regression)** | 线上真实 badcase 回流 | 防止修好一个弄坏三个 | 每条线上事故必须落一条进来 |

**分层抽样怎么做**（这是代表性落地的地方）：

1. 拉取时间窗内真实 trace（如最近 14 天），按**切片维度**分层
2. 每层按比例随机抽（不是人工挑"典型案例"——人工挑会挑掉难例）
3. 去重（同一模板化输入的多次出现只留一条）
4. 脱敏（PII → 占位符）
5. 人工标注期望结果（双人标注 + 争议仲裁）

**切片维度表**（每个产品按实际增删，至少保留前三类）：

| 维度 | 例子 | 为什么必须切 |
|---|---|---|
| **意图类型** | 咨询 / 投诉 / 售后 / 闲聊 / 恶意 | 不同意图的正确行为完全不同 |
| **输入长度与结构** | 短 / 长 / 多轮 / 结构化表单 / 含附件 | 长上下文是模型失效重灾区 |
| **语言与格式** | 中文 / 英文 / 混合 / 含表情 / 含代码 | 混淆率与格式漂移按语言差很多 |
| **难度与长尾** | 常规 / 边界 / 罕见 | 平均分的保险箱在这里 |
| **用户分群** | 新客 / 老客 / VIP / 免费用户 | "谁被服务得更差"只在这里看得见 |
| **失败模式** | 幻觉 / 过度自信 / 拒答 / 格式漂移 / 越权 / 注入 / 隐私串号 | 每个失败模式都要有专属切片 |

## 2. 判分规范

### 2.1 判分优先级（从硬到软）

| 优先级 | 方式 | 适用 | 可信度 |
|---|---|---|---|
| 1 | **确定性规则**（正则 / JSON schema / SQL 校验 / 精确匹配） | 结构化输出、可枚举条件 | 最高，100% 可复现 |
| 2 | **LLM-as-judge**（必须先过人工校准） | 开放式质量、语义正确性 | 高，**但前提是校准过** |
| 3 | **人工标注** | 规则覆盖不到、judge 判不了的 | 最高但最贵 |

**能用规则判的，绝不用 judge 判。** judge 只用在规则判不了的地方。

### 2.2 judge 的强制校准流程

```
① 抽 100 条黄金集样本（覆盖全部切片）
② 两个标注员独立打分
③ 算一致率与 Cohen's κ
④ κ ≥ 0.80 或 一致率 ≥ 85% → judge 可用于门控
   否则 → judge 分数只能当参考，不能当门控证据
⑤ 校准结果写进记录卡（含 n、κ、一致率、日期、rubric 版本）
```

**机械执行**：`python3 scripts/eval_stats.py kappa <judge.jsonl> <human.jsonl>`
（两个文件按 `case_id` 对齐，字段 `{"id": ..., "pass": true|false}`）。

**rubric 改版 = 全部历史分数作废重跑。** rubric 版本必须和分数一起存档。

### 2.3 pairwise 胜率 > 绝对分

绝对分（1–5 分）不可比、不可复现、跨版本漂移。**用 A/B 成对比较**：
同一输入下两个版本（或方案 A vs 方案 B）由 judge 判谁更好，报 **A 胜率 + 置信区间**。

胜率 52% 和胜率 78% 是完全不同的两件事，别把前者写成"接近 50%，说明差不多"——
**它也可能是"没有差异"，也可能是"样本不足看不出来"，两者的动作完全不同。**

## 3. 指标与阈值

### 3.1 必须分开报的四组指标

| 组 | 指标 | 阈值写法 |
|---|---|---|
| **质量** | 逐切片通过率 | 目标值 + 样本量 + Wilson 95% CI 下界 ≥ 阈值 |
| **可靠性** | pass@k、consistency@k | "10 次里至少 8 次对"（k 写死） |
| **安全** | 安全切片通过率 | **容忍度 0**，单条不通过即该切片判否，不进平均 |
| **成本与延迟** | 每次成功成本、P95 延迟 | 上限写死 + 超限降级动作 |

**平均分单独看是危险的**：质量 92% 可能是 8 个切片各 95% 加 1 个合规切片 0% 平均出来的。

### 3.2 阈值一律用 CI 下界

```
不达标：pass rate ≥ 90%
达标：  pass rate ≥ 90% 且 Wilson 95% CI 下界 ≥ 85%（n 与分母写死）
```

工具：`python3 scripts/evidence_stats.py wilson <成功数> <样本数> 0.95` → 直接出下界。
需要多少样本：`python3 scripts/evidence_stats.py required <基线比例> <目标下界>`。

**分母必须写死**：80/200 还是 80/全部线上请求？分母一变，达标与否就翻转。

### 3.3 成本-质量 Pareto

不只看质量曲线，要看**"每提升 1pp 通过率，多花多少钱、多长多少延迟"**。
拐点之后继续加成本换质量是浪费；拐点之前省成本就是在卖质量。**拐点写进记录卡。**

## 4. 回归门禁（CI gate）

**这是 eval 集最主要的存在理由。** 没有回归门禁的 eval 集只是又一份报告。

### 4.1 触发全量评测的变更

| 变更类型 | 是否全量跑 |
|---|---|
| 改 prompt / 系统提示 | **是** |
| 换模型或模型版本 | **是** |
| 改检索策略 / embedding / 切分 | **是** |
| 改温度、top_p、最大 token | **是** |
| 改工具调用逻辑 / 编排顺序 | **是** |
| 改 UI 展示层（不改输出） | 否，但需跑冒烟子集 |
| 改代码里的无关分支 | 否 |

### 4.2 阻断规则

**本节是 eval 阈值的唯一真身。** 其他文件（`domain-standards.md` 等）只引用这里，
不重复写数字——两处各写一份，迟早会漂成两个互相矛盾的数字。

```
基线版本号：eval-v2026-10-24
阻断条件（任一成立即不许合并/上线）：
  ① 总体通过率相对基线下降 > 2pp
  ② 任一切片通过率相对基线下降 > 5pp
  ③ 任一安全切片出现失败（容忍度 0）
  ④ P95 延迟上升 > 30%
  ⑤ 单位成功成本上升 > 20%
```

**机械执行**：`python3 scripts/eval_stats.py gate <results.jsonl> --baseline <baseline.jsonl>`
（默认阈值就是上面五个，命令行参数可临时放宽但**不得写入门控**——阈值要在阶段 8 事前定死）。

**基线必须版本化存档**（eval 集 + 判分脚本 + 基线分数三者一起）。没有版本化的基线，
回归对比就是"我记得以前好像还行"。

### 4.3 线上 badcase 回流

每次线上事故 / 每次人工改写被拒绝，**必须落一条进回归集**，带 trace_id 与根因分类。
没有回流机制的 eval 集会迅速过期——它测的是三个月前的产品。

## 5. 失败模式分类学

**不许只报一个平均分。** 每个失败模式要有专属切片与专属阈值。

| 失败模式 | 症状 | 典型检测方式 | 默认容忍度 |
|---|---|---|---|
| **幻觉** | 编造不存在的政策/价格/承诺 | 事实核验规则 + judge + 抽检 | 0（对外场景） |
| **过度自信** | 不确定却用确定语气 | judge + 置信度校准 | 低 |
| **不当拒答** | 能答却拒答（成本转嫁给用户） | 规则：应答样本被判拒答 | 低 |
| **格式漂移** | 不符合约定结构 | JSON schema 校验 | 0（下游要解析） |
| **越权** | 访问/执行超出授权 | 权限断言 + 红队 | 0 |
| **提示注入** | 被输入内容劫持指令 | 对抗集 | 0 |
| **隐私串号** | 引用到别的用户的数据 | 跨用户对照测试 | 0 |
| **延迟超时** | 超时未返回或降级失败 | 压测 + P95 | 中（看业务） |
| **成本超限** | 单次成本超预算 | 成本埋点 | 中 |

**每个切片单独报通过率 + CI 下界。** 容忍度 0 的切片**不进任何平均值**。

## 6. 生命周期与责任人

| 动作 | 频率 | 责任人 |
|---|---|---|
| 黄金集扩充（新增真实切片） | 每月 | 产品 + 数据 |
| 黄金集重标（rubric 改版 / 真实分布漂移） | 季度或漂移触发时 | 标注负责人 |
| 留出集重建（被看过就作废） | 每季度 | 数据 |
| 对抗集更新（新的攻击手法出现时） | 每月 | 安全 / 红队 |
| 回归集回流（线上 badcase） | 实时 | 一线值班 |
| 全量评测跑一次 | 每次相关变更（CI） | 交付负责人 |
| 影子模式对比（真实流量旁路） | 上线前 + 每周 | 数据 |

**漂移检测**：监控线上输入分布（按切片维度）与黄金集分布的差异。
分布漂了而评测集没跟上 = 你在用三个月前的地图开车。

| 阶段 | 必须交付的 eval 产物 | 门控补充条件 |
|---|---|---|
| **8 制定验证计划** | eval 集规格书（四层结构 + 切片表 + 判分方式 + 判分器校准计划） | 无 eval 集规格 → 不得 GO |

| **10 可行性** | 单位成本模型 + 延迟预算 + 成本-质量 Pareto 初步曲线 | 无成本上限 → 不得 GO |
| **13 上线准备** | 回归门禁配置 + 基线版本号 + 影子模式对比结果 + kill switch 演练记录 | 无基线或无回滚 → 不得 GO |
| **14 试点** | 试点期线上指标（采纳率 / 人工改写率 / 拒答率 / 升级率）+ 回归集回流条目 | 未跑过 eval 或有安全切片失败 → 不得 GO |

| **20 AI 审计** | 全量审计报告（逐切片 + 失败模式 + 偏差 + 滥用 + 人工接管 + 成本） | 达场景要求且失败可控才 GO |

## 9. 反模式清单

| # | 反模式 | 症状 | 为什么差 |
|---|---|---|---|
| E1 | **自己出题** | eval 集全是同事编的干净输入 | 代表性是假的，测的是"我会不会出题" |
| E2 | **只报平均分** | "准确率 92%" | 合规切片 0% 被平均掉了 |
| E3 | **judge 未校准就当门控** | LLM 给 LLM 打分 | 用一把没校准的尺子量长度 |
| E4 | **绝对分当结论** | "用户满意度 4.2 分" | 不可比、不可复现、跨版本漂移 |
| E5 | **eval 集只增不减地过期** | 一年后还在测老分布 | 用旧地图开车 |
| E6 | **有 eval 无回归门禁** | 报告很厚，改 prompt 没人跑 | eval 变成一次性表演 |
| E7 | **安全切片混进平均** | "总体 95% 通过" 含合规切片 | 容忍度 0 的东西没有平均分 |
| E8 | **失败模式只测了准确率** | 没测幻觉/注入/越权/串号 | 事故恰恰发生在这里 |
| E9 | **用 judge 分数替代人工验收** | "LLM 觉得没问题" | 循环论证 |
| E10 | **没有基线版本号** | "我记得以前还行" | 回归对比不可复现 |

## 11. 这一轮 evals 不能证明什么

必须在记录卡里写明（不许省略）：

| 已能证明 | 尚不能证明 |
|---|---|
| 在**这一份冻结的 eval 集**上，各切片的通过率与 CI 下界 | 真实流量上的长期质量（分布会漂） |
| 某次变更相对基线没有退化 | 换模型/换供应商后的表现 |
| 安全切片在**已构造的对抗样本**上未失败 | 没被构造出来的攻击手法 |
| 单位成功成本与延迟在测试负载下达标 | 峰值负载下的表现 |
| 判分器与人工的一致程度 | 判分器没覆盖的语义维度 |
| 线上 badcase 已回流进回归集 | 回流机制不会漏 |

**禁止把"eval 通过"写成"质量达标"。** 前者是"在某个冻结测试集上过了阈值"，
后者是一个更强的、目前没有证据支持的命题。
